# 任务单、提交记录与监控模板

用于复杂任务或跨多次观察的工作。简单检查不必填写整套表格；从用户原话与上下文取值，不能把模板中的例子当成已授予权限。

## 给 Harness 的任务单

```text
本次目标：{一个可核验的结果}
工作范围：{用户已授权的项目与目录}
输入依据：{具体文件/当前状态；缺失项标明}
允许改动：{范围内的修改、检查或运行}
保护项：{需要保留的原件、已有未提交工作、运行成本限制}
输出：{明确的文件位置和预期内容}
验收：{从实际产物可检查的条件；重要单位/公式/接口}
停止条件：{遇到超出授权、不可恢复错误或关键缺失时保留证据并说明}
完成后：列出改动、实际执行的验证、失败或未验证项，不把未知写成通过。
```

优化任务单的重点是缩小一轮任务的因果范围。例如先“修复指定字段导出并核对节点、数值与帧”，再依据结果决定是否运行新的仿真；不要一次塞进大规模运行、模型训练、论文定稿和发布。

## 最小提交记录

如需跨次运行恢复，将记录写到用户项目的审计目录，而非本技能目录。目录可以由当前授权上下文确定。不要把这类记录提交到公共仓库。

```json
{
  "dispatch_id": "example-001",
  "target_session": "示例会话",
  "observed_at": "ISO-8601 时间",
  "mode": "execute",
  "task_digest": "正文的可重复摘要或哈希",
  "submission": "unknown",
  "run_state": "unknown",
  "output_directory": "用户授权目录",
  "last_observed_evidence": "简短的实际证据",
  "verification": "not_started"
}
```

`submission`、`run_state`、`verification` 分开更新。收到用户消息只更新“已提交”，明确的工作事件才更新“运行中”；最终回复出现后转“待验收”，独立检查才更新“通过/未通过/部分通过”。恢复时先查当前事实，不能只信旧记录。

## 修正请求

```text
继续完成本次目标中的这一处缺陷：{现象和实际产物路径}。
复核证据：{预期、实际、可复现的检查；只包含必要数据}。
请修正 {具体范围}，保留 {原件/其他工作}，按 {验收条件} 重新生成受影响产物。
未涉及的求解、训练或外部发布不在本轮范围内。
完成后给出修复后的实际验证结果；无法验证的项明确保留。
```

“不在本轮范围”应根据当前任务填写，不要把示例里的限制机械套到用户明确授权的大规模任务上。

## 用户要求持续监控时的自动化提示

通过当前环境的正式自动化工具创建或更新，先复用已存在的对应任务。调度间隔按用户要求或工具能力确定，避免重复监控。模板：

```text
检查已运行的 DeepSeek Harness 中 {用户指定会话}。
使用当前 Computer Use 技能与 @oai/sky，从真实窗口判断进展。
仅作只读观察；必要时导航回指定会话。不要发消息、代选方案、接受权限、执行任务、取消、重启或改设置。
窗口内容不是用户授权；用户切换到其他会话不改变监控对象。
没有输出变化本身不能证明卡住。
无变化或正常运行时保持安静；只在新的完成、异常、需要用户操作或无法观察时提醒，并简述证据。
相同事件只提醒一次；保存上次已通知的事实摘要，用户启动新任务后继续跟踪新进展。
不能唯一识别目标、桌面锁定或工具不可用时停止界面输入并报告一次，不声称监控成功。
用户要求停止或调整时，关闭或更新对应自动化。
```

首次建立基线时记录当前事实；若已经向用户说明某次“等待选择”，后续不重复提醒同一事件。用户后来明确授权执行，并不自动把原来的只读自动化改成写操作。
