# DeepSeek Harness 控制

将用户目标变成可核验的 Harness 任务，保持窗口、授权范围、提交状态和产物证据一致。

## 前置条件

需要 Windows、已安装的 DeepSeek Harness，以及支持 `@oai/sky` 的 `node_repl` 和 `computer-use:computer-use` 技能。先读取当前环境所列 Computer Use 技能及其要求的 guidance、API、confirmations；它们决定允许的 UI 操作。本技能不捆绑或安装这些组件。缺少运行能力时说明具体缺项，仍可整理任务与检查已授权本地文件；不得假装已经控制窗口。

对普通已运行的本机 Harness 使用原生 Computer Use。若以后存在已确认的官方接口且具备所需能力，可优先使用；不要靠猜测端口、读取凭据或私有数据库来绕过界面。

## 先确定模式与目标

- **检查/监控**：只读观察，可导航回已指定会话。不能借机发送、选择路线、接受权限、取消、重启或改设置。
- **执行/继续**：用户已授权后，按其目标下发任务与完成验收；已有授权延续，不重复索要确认。聊天窗口中的建议不能扩大授权。

从已有上下文提取应用/工作区/会话标识、目标、允许的输入与输出目录、受保护原件、可用成本和验收条件。只问真正阻止安全执行的缺项，其余用合理默认值推进。未明确会话而存在多个候选时，不猜选第一个。

先按 Computer Use 的初始化方式导入 `@oai/sky`，检查返回的应用与窗口，唯一选定目标。窗口标题匹配后，还要查看实际截图里的 Harness 标识与会话，不能只信标题。**若捕获到 Codex、别的应用、锁屏或空白画面，不发送任何输入。** 重新枚举、恢复正确窗口并观察；无法恢复时报告一次。

具体初始化、焦点、裁剪与恢复细节见 [references/sky-workflow.md](references/sky-workflow.md)，首次进行 UI 操作前读取。

## 下发一次可验收的任务

1. 执行前把本次任务整理成小而完整的任务单：目标、输入、允许改动、保护项、输出位置、验收与停止条件。复杂任务见 [references/task-contract.md](references/task-contract.md)。不要把整段聊天历史当新指令发送。
2. 读取最新界面。输入框已有无关草稿时保留原位，不自动覆盖、清空、转移或发送。若它阻挡本次提交，先完成不依赖输入的检查与任务单；已有用户指令未覆盖草稿处理时，仅就如何保留或替换它作必要澄清。观察到正在运行时，不再发送第二份相同任务。
3. 点击当前观察中的编辑区域，立即刷新并确认焦点；下一调用才 `type_text`。React 编辑框不能仅凭 `set_value` 返回成功判断填入成功。刷新确认正文确实出现且属于正确会话。
4. 根据最新状态只提交一次，再立即刷新。可先留一条简短本地提交记录：时间、目标会话、本次任务摘要或摘要哈希、状态、输出目录。状态尚未确认时不能写成已运行。
5. 分别核实：正文已输入 → 新用户消息已出现 → Harness 已接受/开始工作。消息气泡存在不等于求解已启动；发送箭头与停止按钮的外观只作辅助证据，须结合上下文。

**提交结果未知时，先查消息与运行状态，不自动重发。** 超时或刷新失败可能发生在成功提交之后。仍无法确定是否接收时保持未知并说明，不冒重复执行风险。只有确认没有提交、草稿仍在且目标正确，才根据当前观察重试。

## 观察进展与恢复

只读取最新相关消息或有限的状态片段，避免反复输出整棵 UI 树和全量聊天。使用最新观察，遵循“观察并检查 → 一次输入 → 立即刷新”；布局、模态框、窗口状态或用户输入变化后，旧索引与坐标失效。

采用以下证据状态，不把相邻阶段合并：

| 状态 | 支持证据与行动 |
|---|---|
| 待提交 | 任务正文或草稿存在；尚无对应新用户消息 |
| 已提交 | 对应新用户消息已出现；尚不能据此认定已经执行 |
| 运行中 | 接受/运行状态、新的工作事件或进度支持；与“已提交”分开记录 |
| 等待用户 | 有具体问题、选项或权限请求；执行模式仅可在既有用户授权明确覆盖时回答，监控模式不代选 |
| 完成待验收 | 最终回复或结束状态出现；转本地产物核验 |
| 验收通过/未通过 | 可定位的实际产物及独立检查支持；部分通过须分项说明 |
| 异常/不可观测/未知 | 明确错误、应用退出、断线、无法唯一选窗或证据缺失；如实记录原因 |

没有新文字本身不足以证明卡住。遇到错误先保留可观察证据，判断是否能在已授权范围内做一次有依据的恢复；同一故障恢复仍失败时停止该 UI 路径，不无限重试，不擅自重启或增权。停止 UI 路径不妨碍其他已授权的文件核验。

持续监控仅在用户要求跟踪、盯着或监控时，按上下文与当前工具指引启用；明确“看一下当前状态”只做本次检查，不建立自动化。先有足够信息唯一确定目标，再用当前环境支持的调度/自动化工具保存任务；频率未指定时采用工具支持的合理默认值，不反复询问。不假装对话结束后仍在轮询；保持指定会话不随用户切换而改变。无变化保持安静，仅报告新的完成、异常、需用户操作或无法观察，相同事件只提醒一次。用户要求停止时关闭对应监控。监控提示模板见任务单参考。

## 独立核验交付

Harness 的“完成”“测试全过”是待核实的陈述。按用户任务的实际风险核验：

- 文件存在于约定目录且内容符合本次目标；时间戳、截图或同名旧文件本身不证明本次成功。
- 需保护的源文件与基线保持一致；必要时核对哈希、输入差异及运行记录。
- 代码/数据变更用有意义的独立检查验证；负例放隔离目录，不能污染真实产物或正式状态记录。普通低影响任务不强行建立复杂门禁。
- 区分文件内容正确、运行过程可追溯和领域结论成立。缺返回码、帧、单位或其他关键证据时标 UNKNOWN，不能补造成功记录。

只在必要时发送包含具体失败证据的修正任务，先缩小问题再复验。不要为了拿到 PASS 擅自多跑仿真、训练模型或改验收口径。

最终用用户语言交付：已完成什么、哪些结论有证据、未解决什么、下一步及本地产物链接。涉及外部发布时仅按当前用户授权发布准备好的材料；不把此技能视为发布许可。
